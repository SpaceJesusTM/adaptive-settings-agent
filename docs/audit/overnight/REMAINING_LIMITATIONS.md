# Remaining limitations

| Priority | Weakness at the first audit | Controlled evidence and current state |
| --- | --- | --- |
| 1 | A newer protection only warned about an older proposal. The older proposal could still change a protected control. | In the [pending protection fixture](../../../scripts/run_overnight_benchmark.py), an earlier CS2 Reflex proposal applied under the first audit. The candidate rejects the same Apply atomically and a direct manual edit succeeds. The [browser regression](../../../frontend/e2e/overnight.spec.ts) uses VALORANT VSync and applies only the other selected changes. |
| 2 | Model composition can concentrate the deadline on a single response. A later timed-out batch could discard earlier results. | The frozen mixed request fell back on one of three first-audit runs. A [delayed-second-batch test](../../../backend/tests/test_overnight.py) preserves two checked recommendations in the review tray, with the response labelled as partial. A single composition pass still needs to finish to return structured decisions. |
| 3 | Named settings could receive relevant prose with no reliable shortcut to their canonical row. Pending recommendations could be described as past player edits. | The first audit supplied the required Ambient Occlusion link in one of three live runs. The candidate binds an unambiguous target server-side and reads the pending and current values separately for a status question. The history text filter still depends on bounded phrasing and known setting names. |
| 4 | The system could promote one manual interaction into a general pattern and used a mostly fixed order for Discover. | [Matching settings with different histories](PERSONALIZATION_EXPERIMENTS.md) isolate independent manual choices from accepted recommendations. An experimental policy can turn repeated evidence into a contextual inspection prompt. It cannot infer why a player made those choices from simulator events alone. Normal app reopening preserves the same session ID, so the cross-session experiment used explicit research session boundaries. |
| 5 | Scope and retrieval mostly depend on recognizable vocabulary and syntax. | Temporal exact requests, bounded comparative trade-offs and explicit split requests improved. Unfamiliar phrasing and underspecified references still expose gaps. See [the semantic experiments](SEMANTIC_UNDERSTANDING.md) for the limits of the additional model pass. |
| 6 | Checks establish canonical behavior and task suitability. | A scripted rubric cannot establish that a player discovered, understood, or would use a control independently. Measure those outcomes in the participant study described in [the project traceability guide](../PROJECT_REQUIREMENTS.md). |

A simulated goal update and a manual setting edit can arrive during inference. The candidate compares the captured session, profile, locks, hardware and goal context before writing a proposal. It drops only recommendations for individually revised settings when the rest of the captured context still matches. The proposal service rechecks protections, revisions and value validity at Apply. These checks cover the simulator database.

Temporal wording marks the request as session-specific for interpretation. Applying a value still commits a normal simulator setting. A value set “for tonight” stays in place until the player changes or undoes it. A narrowly scoped restore request reads the previous committed value.
